## Task 6：编组拖到末尾只能落最深层 → 改 X 决定层级（左移进入上一级）
- 根因：编组路径派生自变量名（`color/brand/primary`），旧拖拽只重排扁平 `group_order`，**永远改不了层级**（层级由路径定死）。所以"向左移进入上一级"必须**重定父级（reparent，改路径）**，不能只重排。
- 做法：
  - `list_drag.rs` 新增 `ListDrag::finish_leveled(ui, |rows, from, p| -> Option<(to,y,x0,x1)>)`，让调用方按指针决定落点与插入线 x 跨度（替代原 `finish` 的固定全宽线）。
  - `variables_panel.rs` `group_rows` 拖拽落点改用 `group_drop_slot(rows, from, p, &ids, base)`：
    - `base = r.min.x + 8`（0 级组标签 x）；`level = floor((p.x - base)/16)`，并 clamp 到目标组自身的 level。
    - 指针在更深行（如 `primary` L3）自身缩进 → level 3（brand 下的同级）；**左移到 brand 缩进 → level 2（color 下同级）；再左 → level 1（顶级）**。
    - 插入线 `x0 = base + level*16`，`x1 = 行右`：层级越低 x0 越靠左 → 线"更长"（用户要的"更长的横条，上一级那个宽度"）。
  - `apply_group_drop`：按 level 取目标组前 `level-1` 段作新父级；把被拖组及变量 `variable.update` 重命名为新路径（一个 batch，单步撤销）。`group_order` 同步：删旧+子孙，按指针位置插新路径；`st.group` 跟随。
  - **安全**：重命名前先 `HashSet` 预检目标名是否已被占（避免 batch 部分失败导致半改名）。引擎 `variable.update` 对重名也会拒，双保险。
- 测试：新增 `group_drop_level_follows_pointer_x`（纯函数 `group_drop_slot`：验证 level 随 x 左移递减、父级线更宽、末尾 clamp 到 space 的 level 1）。`variables_view_tests` 全过（未引入回归）。
- **补丁（同日）**：`group_drop_slot` 的无移动保护原写法 `from_level == <同值重算>` 恒为真 → 会把"同 Y 但改了 level"的 reparent 也误杀。
  改为先算 `level` 再比 `level == from_level`：同缝隙且层级不变才视为无移动；同缝隙但层级变了（原地左移升层）仍 reparent。`variables_panel` 测试 2 passed、`variables_view_tests` 42 passed 仍全绿。

## Task 6 明显 bug 修复（reorder 变 no-op + 顶部死区）
- **现象**：拖动编组到「同层级不同位置」松手后**原样弹回**（没移动）；且拖到列表最顶上也落不进去。
- **根因**：Task 6 把旧 `drag.finish` 换成 `finish_leveled`+`apply_group_drop` 后，`apply_group_drop` 里
  `if new_path == old { return; }` 把「纯重排（同 level、path 不变）」直接 return 了 —— 重排被整个吞掉。
  （旧逻辑靠 `drag.finish`→`drop_slot`→`Dropped{from,to}` 写 `group_order`，已被替换，新的只处理 reparent。）
- **修法**：
  - 去掉早退。`new_path != old` 才做变量改名 batch + 冲突预检；`new_path == old` 走纯重排（不改名）。
  - 重排统一用「移动集」：`ordered` 里 `== old` 或 `starts_with("{old}/")` 的组（含子孙）整体取出、改名、按原相对序插回 `at`（`moved.into_iter().rev()` 保证父在前子孙在后）。这样 reparent 时子孙组也跟着换前缀、`group_order` 不丢项。

## ⚠️ Task 6 严重回归修复（每帧都 apply → 抽动/疯狂建子项/层级跑到末尾）
- **现象（用户报"Bug更严重了"）**：拖动时疯狂抽动；展开层级时子级被拉到列表最后而不是挂在父下面；拖动时疯狂创建子项。
- **根因（致命）**：`finish_leveled` 的 `resolve` 闭包**每帧**都为画插入线而解析落点，而调用方
  `let mut info=None; let _=drag.finish_leveled(|...|{ info=Some(d); ... }); if let Some(d)=info { apply_group_drop(...) }`
  —— **闭包外无条件 apply，导致拖动每一帧都在改名/重排**：`variable.update` 每帧发一次 → 疯狂建子项；`group_order` 每帧重写 → 抽动；`at` 偶尔落到 `ordered.len()` → 层级被推到末尾。
- **修法**：
  1. **只在松手时 apply**：`let dropped = drag.finish_leveled(...); if dropped.is_some() && let Some(d)=info { apply_group_drop(...) }`。
     `finish_leveled` 只在 `released` 时返回 `Some(Dropped)`，用它做闸门。
  2. **禁止拖到自己/自己子树**：`apply_group_drop` 开头 `if ids[t]==old || ids[t].starts_with("{old}/") { return }`（否则成环且丢锚点）。
  3. **`ordered` 补齐**：编组由名字派生，改名后新组可能不在 `group_order` 里 → `at` 的 `position` 找不到就 `ordered.len()`（插到末尾，正是"没挂在父下面"）。构建 `ordered` 后把 `ids` 里缺的组 append 进去，保证目标一定找得到。
  4. **显示顺序改成真·树序**：新增 `tree_order(list, order)`——按 parent→children 建树后 DFS，兄弟按 `group_order`（无则字母序）。原来只是对扁平列表按 `group_order` 位置 `sort_by`，缺组的会掉到末尾。`group_rows` 里 `let list = tree_order(&groups(...), &order)`。
- 测试：`variables_panel` **4 passed**（新增 `tree_order_keeps_children_under_their_parent`），`variables_view_tests` **42 passed**。`cargo build -p figcraft` EXIT=0。
- ⚠️ 用户当前文档可能已被上一版 buggy 构建**每帧改名**污染（多出一堆子组）；`group_order` 是会话内偏好，重启即清空，但变量改名是真实引擎命令、会留在文档里，需用户自行 undo 或重载。

## Task 6 插入线长度修正（部分情况线太长）
- **现象（用户报）**：核心逻辑没问题，但插入线在"部分情况"下长度不太对。
- **根因**：`group_drop_slot` 里 `level = floor((p.x-base)/16).clamp(0, max_level)` —— **下限是 0**。但编组永远 ≥1 级（0 级是 "All variables"）。指针拖到最左（`p.x < base`）时 level 被夹到 0，`x0 = base`（对齐 "All variables"，比 1 级还长一截），可落点仍是顶级（`new_parent=""`）——同一个"顶级"结果出现两种线长。
- **修法**：`let level = floor((p.x-base)/16).clamp(1, target_level)`（去掉 `max_level`；编组没有 0 级，且不能比目标组更深）。顶级恒用 1 级宽度 `x0 = base + 16`。
- 几何核对：label x = `base + level*16`（`base = r.min.x+8 = alloc.min.x+16`），`x0` 正好对齐该级标签；`x1 = last.max.x` = 行右边缘（= 高亮块右边缘）。所以线 = [该级缩进, 行右]，层级越浅越长。
- 测试：`variables_panel` **4 passed**（`group_drop_level_follows_pointer_x` 加了"拖到最左仍是 level 1、x0=base+16"断言），`variables_view_tests` **42 passed**。`cargo build -p figcraft` EXIT=0，已用计划任务重启（PID 32056）。

### 再修正（同日，用户报「空组拖不进东西做子组」）
- **需求**：没有子组的组（如 `sh`/`space`），别的组拖不进去当子组。

  - `gap = count(center.y < p.y)`；`bottom = gap >= n`；**锚点 `anchor = rows[gap.min(n-1)].0`**（边界下方那一行）；`anchor_level = ids[anchor] 层级`。

### 再修正（同日，用户报「线跟鼠标/实际落点不匹配」）
- **根因**：线画在「指针的原始边界」，但实际落点由 `ordered`+`tree_order`（树序）决定。当 **层级比锚点浅**（向左拖升层）时，元素不可能停在更深子树的中间，实际会落到**该祖先子树的最末尾**，可线还画在中间边界 → 线≠落点。
- **修法**：`group_drop_slot` 增加 `vis`（元素真正落到的可见下标），线 Y 用 `rows[vis].min.y`（`vis>=n` 用 `last.max.y`）：
  - `bottom` → `vis=n`（末尾）；
  - `into` → `vis=gap+1`（锚点下一行）；
  - `level==anchor_level` → `vis=gap`（锚点顶）；
  - `level<anchor_level` → 取 `anc=ids[anchor] 前 level 段`，`vis = anc 子树末（排除被拖组自身） + 1`。

### ❌ 上一条「线吸附到子树末尾」是错的 → 回退为扁平顺序（同日，用户纠正）
- **用户反馈**：「线的长短决定不了层级了，默认都插到最下面」「光标和线距离非常大，光标在老上面」。

- **修法（关键）**：**显示顺序改回扁平**——`list` 按 `group_order` 位置 `sort_by`（无则字母序），**不再 tree_order**。缩进只由路径决定，不强制树序。这样 `ids[k].0=k`、`ordered==扁平显示序`，线在 `gap`（光标那条缝）、插入也在 `gap`（`pos(anchor)=gap`）→ **线/光标/落点三者天然一致**。
  - `group_drop_slot` 的 `y` 回退到边界：`bottom→last.max.y`；`into→rows[gap].max.y`；否则 `rows[gap].min.y`。
  - 删除 `tree_order` 函数与其测试；`list` 用回扁平 `sort_by`。
  - 测试：删 `..._snaps_to_the_subtree_end`，新增 `group_drop_line_stays_at_the_pointer_boundary`（拖 filed 到 sh 上方、level 1 → `(level, y)==(1, 1*32)`，即仍在光标边界）。panel **7 passed** / view 42。
- ⚠️ 遗留风险：`rename_group` 未同步 `group_order`，改名后的新路径不在 order 里 → 扁平排序会把它甩到末尾（用户之前报过类似"跑到最后"）。若再出现，需在 `rename_group` 里把 `g`→`renamed`（含子孙前缀）同步进 `st.group_order`。
